# Skill-read-guidance retrospective

## Outcome

PR (draft): https://github.com/jon-devlapaz/tink-substrate/pull/3

Agents could not load required skills by following printed guidance. Two
repositories own the broken text: tink writes the `(full: .tink/.active/...)` rule
line, and tink-sdlc prints `tink mount NAME --payload`. Source fixes already
existed as jon-devlapaz/tink#94 and jon-devlapaz/tink-sdlc#43. The user chose to
adopt them, not duplicate them.

This PR pins Substrate's bundled tink-sdlc to candidate `9172e2d` (head of #43),
adds a locked reproduction test, and rewords the pin docs. It stays draft until #43
is merged and the pin points at merged history. No merge occurred.

## Evidence and limits

- Reproduction: tink 1.0.48 `tink mount unslop --payload` exits 2; the rule path is
  absent until a plain mount. The planner, the builder and the PR reviewer all
  hit the same failures independently (`handoff.md`, `05-deploy/output/REVIEW-findings.md`).
- Test `tests/test_skill_read_guidance.py` failed at `328a230` and passes at
  `9172e2d`. Independent review accepted it before the fix
  (`03-build/output/test-review.md`); `test-lock.json` protects it.
- 49 tests pass. SDLC verification is current: 5/5 items, of which 3 are proven by
  check and 2 are attested (docs wording, trial).
- Remote CI: 4/4 jobs passed at 3693e72 (Ubuntu/Python 3.11, macOS/Python 3.14).
- Fresh-agent trial (`trial/`): a new agent with a temp install of this branch,
  tink built from #94 and a temporary library copy loaded its required skill by
  running the printed line exactly. Exit 0, 2458 chars of payload
  (`payload-check.json`). The logging wrapper captured only `tink` calls; the
  claim of no path probing or install edits rests on the agent's own report.
  Control with the current tools reproduced both failures.
- Not exercised: a routed skill (the router exited 2 at every stage open, so no
  launch prompt carried a pick), stages 3-5 in the trial, and the released tink.
- Independent PR review: ACCEPT, no Important findings, five Minor ones. The PR
  body now states attested items and the logging limit.

## Failures and repairs

None in the product change. The reviewer noted the stage-4 `local-ci.md` install
ran from a dirty tree; its clean install of HEAD replaces that evidence.

## Obstacles and interventions

- The fixes already existed in two open PRs from an earlier session. Asking the
  user before building avoided duplicate work. The user also asked for a plain
  explanation of #94 and #43 before approving; the first brief prompt assumed
  context they did not have.
- `sdlc.py stage 3` refused because the planning worktree already used the run's
  branch name. Used `--here`; it does not commit `runs/`, so the coordinator did.
- Every agent in this repo still saw the old guidance, because this repo's own
  `_system/` is tink-sdlc 1.18.2 and the installed tink is 1.0.48. They loaded
  skills only by working around it. That is expected until both fixes ship.
- The dashboard showed the new PR link only after a server restart.
- No permission prompts or human coaching for implementation.

## What this taught us

The bug lived in text generated by two upstream tools, while the user saw it
through Substrate. Substrate's job was to pin the fixed version and prove the
combination from a clean install. That trial is the evidence neither upstream PR
had alone.

Decision: proceed. No workflow change in Substrate is justified by this run.
Smallest next steps, all needing the user:
1. Merge or release tink-sdlc#43 (coordinate its version with #42), then repin
   this PR to the merged revision and mark it ready.
2. Merge and release tink#94, then install the new tink so `tink use` writes the
   readable line.
3. Separately, upgrade this repo's own `_system/` to the fixed tink-sdlc so its
   agents stop hitting the old hint.

## Delivery result

Remaining decisions: merge of tink#94, tink-sdlc#43 and this PR. The delivery
archive path is recorded in the external work record.
